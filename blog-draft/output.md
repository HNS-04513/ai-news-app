# 클로드 코드로 하는 바이브 코딩, 속도보다 통제가 먼저다

## 서론

2025년 2월, Andrej Karpathy가 "바이브 코딩(vibe coding)"이라는 말을 처음 썼다. 그는 "vibes에 몸을 맡기고 코드가 존재한다는 것을 잊는" 코딩이라고 표현했다. 배경에는 2023년의 발언이 있다. "가장 뜨거운 새 프로그래밍 언어는 영어다."라는 말이다. 원래 뜻은 가벼웠다. 주말 프로토타입이나 작은 실험을 AI에게 맡겨 보는 방식이었다.

시간이 지나며 이 말은 두 갈래로 나뉘었다. 하나는 비판적인 뜻이다. AI가 쓴 코드를 검토 없이 받아들이는 일을 가리킨다. 다른 하나는 넓은 뜻이다. AI 도구와 협업하는 전문 개발 전반을 바이브 코딩이라고 부르기도 한다. 같은 단어를 쓰면서 서로 다른 이야기를 하는 경우가 많다.

이 글은 터미널 기반 에이전트 도구인 Claude Code를 중심으로 바이브 코딩을 살펴본다. 최근 흐름, 장점과 단점, 공개된 사례, 위험을 줄이는 실천법, 어울리는 경우와 그렇지 않은 경우를 차례로 정리한다. 결론을 먼저 말하면, 실무에서 중요한 것은 코드를 얼마나 빨리 만드느냐가 아니다. 얼마나 잘 통제하느냐다.

## 본문

### 최신 트렌드

바이브 코딩이라는 말은 빠르게 퍼졌다. 영문 Wikipedia의 "Vibe coding" 항목을 기준으로 주요 시점을 보면 이렇다. 2025년 3월에 Merriam-Webster가 이 말을 "slang & trending" 항목으로 올렸다. 2025년에는 Collins가 올해의 단어로 골랐다. 2025년 6월에는 Andrew Ng가 "잘못된 명칭"이라고 비판했다. 같은 해 7월에는 WSJ가 전문 엔지니어들의 상업적 도입을 보도했다. 2026년 1월에는 Linus Torvalds가 Google Antigravity로 개인 프로젝트용 시각화 도구를 바이브 코딩했다는 보도가 나왔다.

반대편의 경고도 있다. Simon Willison은 바이브 코딩으로 프로덕션 코드베이스까지 가는 것은 명백히 위험하다고 말한다. 2025년 5월에는 Lovable로 만든 앱 1,645개 중 170개에서 개인정보 노출 취약점이 보고됐다. 이 두 가지는 뒤에서 다시 다룬다.

Claude Code는 이 흐름을 대표하는 도구다. 터미널에서 코드베이스를 읽고, 파일을 고치고, 명령을 실행한다. npm 레지스트리 메타데이터를 보면 패키지는 2025년 2월 24일에 만들어졌다. 글을 쓰는 2026년 11월 19일 기준 최신 버전은 2.1.328이고, 릴리스는 570개가 넘는다. 프롬프트 한 줄로 해 보는 실험에서 에이전트가 여러 단계를 수행하는 워크플로로 무게가 옮겨 가고 있는데, Claude Code가 그 변화의 한가운데에 있다.

공개된 CHANGELOG를 따라가 보면 기능의 방향이 보인다.

- 2025년 6~7월: MCP 연동이 강화됐다.
- 2025년 7~11월: UserPromptSubmit, SessionStart, PreCompact, SessionEnd, Stop, PermissionRequest, SubagentStart 같은 훅 이벤트가 늘어났다.
- 2025년 10월: Explore·Plan 서브에이전트, Skills, 플러그인이 들어왔다.
- 2025년 12월: 플러그인 마켓플레이스 관리와 Claude in Chrome 베타가 추가됐다.
- 2026년: 백그라운드 서브에이전트, 워크트리 격리, 관리형 설정이 나왔고, 9월에는 AGENTS.md 지원이 더해졌다.

사용 표면도 넓어졌다. 터미널, VS Code, 데스크톱 앱, 웹, Remote Control, Agent SDK, 헤드리스 모드(`claude -p`)에서 쓸 수 있다.

업계 전체로 보면 자동완성에서 "작업 단위 위임"으로 이동하는 중이다. 비슷한 명령줄 도구도 잇따라 나왔다. OpenAI Codex CLI가 2025년 4월, Google Gemini CLI가 2025년 6월, GitHub Copilot CLI가 2025년 9월에 나왔다. Cursor나 Windsurf 같은 IDE형 도구의 기능과 점유율은 이번 조사에서 확인하지 못했다. 그래서 여기서는 다루지 않는다.

CHANGELOG를 읽고 내린 추정이지만, 방향은 분명해 보인다. 병렬·백그라운드 에이전트가 늘고, 훅과 권한으로 통제하고, 워크트리로 작업을 격리하고, 플러그인과 관리형 설정으로 팀에 배포한다. 새 기능 대부분이 "더 빨리 쓰기"보다 "더 안전하게 맡기기"에 가깝다. 실무로 갈수록 관건은 생성 속도가 아니라 통제 장치라는 뜻이다.

### 장점

가장 큰 장점은 에이전트가 일을 이어서 처리한다는 점이다. 코드를 찾고, 고치고, 명령을 실행하고, 테스트를 돌리는 과정이 한 흐름으로 이어진다. 반복 작업과 보일러플레이트에 드는 시간이 줄어든다. 다만 효과는 작업 종류와 숙련도에 따라 편차가 크다.

진입 장벽이 낮아지는 점도 크다. 아이디어를 빠르게 프로토타입으로 만들 수 있다. 코드베이스의 맥락을 읽고 여러 파일에 걸친 변경도 처리한다. 프로젝트 규칙은 CLAUDE.md에 적어 두면 에이전트가 따른다.

스스로 고치는 루프도 쓸모 있다. 빌드, 테스트, 린트를 실행하고 오류 메시지를 읽은 뒤 수정한다. Git 작업도 같은 흐름 안에서 처리한다. 큰 변경에는 계획 모드가 도움이 된다. 구현에 들어가기 전에 계획을 보고 승인할 수 있어서, 방향이 틀어지는 일을 일찍 막는다.

### 단점과 위험

가장 먼저 걸리는 것은 코드 품질과 보안이다. 이해하지 못한 코드가 쌓이기 쉽다. 관련 연구가 몇 가지 있다. Veracode의 2025 GenAI Code Security Report는 AI 생성 코드 샘플의 약 45%에서 보안 결함을 찾았다. 다만 시험 과제에 한정된 결과라서 일반화하면 안 된다. GitClear는 AI 도입 이후 코드 중복과 churn이 늘었다고 분석했다. Perry 등(ACM CCS 2023, Stanford)은 AI 보조를 쓴 사용자가 더 불안전한 코드를 쓰면서도 자신의 코드를 더 믿는 경향을 보고했다.

과신도 문제다. METR이 2025년 7월에 발표한 무작위 대조 실험에서, 숙련된 오픈소스 개발자들은 AI를 썼을 때 평균 약 19% 느려졌다. 그런데 본인들은 약 20% 빨라졌다고 느꼈다. 한 연구가 모든 상황을 대표하지는 않는다. 그래도 체감 속도와 실제 속도가 다를 수 있다는 점은 기억할 만하다.

비용도 있다. 구독은 사용량 한도가 있고, API는 토큰 단위로 과금한다. 긴 컨텍스트와 반복 루프는 비용을 키운다. 요금 정책은 자주 바뀌니 직접 확인해야 한다.

보안 측면에서는 권한을 넓게 자동 승인할 때 위험이 커진다. 파일 삭제, 시크릿 노출, 임의 명령 실행이 가능해진다. 프롬프트 인젝션도 고려해야 한다. 마지막으로 디버깅이 어렵다. 직접 짠 코드가 아니어서, 문제가 생기면 구조부터 새로 파악해야 한다.

### 실제 활용 사례

먼저 기업 사례다. 아래 수치는 모두 Anthropic 고객 사례 페이지에 실린 회사 발표 기준이다. 독립적으로 검증된 것은 아니다.

Stripe는 엔지니어 1,370명에게 Claude Code를 전사 롤아웃했다. 발표에 따르면 Scala에서 Java로 옮기는 마이그레이션에서 코드 10,000줄을 4일 만에 이전했다. 수작업으로는 10 엔지니어 주가 들 것으로 예상했다고 한다.

Zendesk에서는 5명으로 이뤄진 팀이 Claude Code와 Agent SDK로 커스텀 에이전트 빌더를 만들었다. 개념 검증에서 얼리 액세스까지 4개월이 걸렸다. 얼리 액세스 이후 7주 만에 에이전트 실행 횟수가 100만 회에 이르렀다고 한다.

Mercado Libre는 개발자 23,000명 이상이 사용한다고 밝혔다. 사람의 감독 아래 에이전트가 1년간 50만 건 넘는 코드 제출을 리뷰했고, 약 9,000개 서비스를 이전했다고 한다. 2026년 2분기 코드 제출은 전년 대비 110% 늘었다. 이 수치는 Claude 전반의 성과일 수 있어서, Claude Code 단독 효과라고 보기는 어렵다.

Travelers는 직원 약 25,000명이 Claude를 쓰고, 병합 코드 소요 시간이 50% 줄었다고 발표했다. 이 수치도 Claude Code만의 결과인지는 분명하지 않다.

개인 프로젝트로는 Hacker News의 "Show HN"에 올라온 것들이 있다. 제목 수준에서만 확인한 내용이다. Claude Code로 ESP32 펌웨어와 UI를 만들고 웹캠으로 화면을 보며 UI를 고치는 프로젝트(claude-code-eyes, 2025년 9월경)가 공개됐다. 에이전트가 반복한 실수를 바탕으로 가드를 만드는 프로젝트(claude-code-mistake-guards, 2026년 10월경)도 공개됐다. 두 프로젝트의 내용이나 성과는 이 글에서 평가하지 않는다. 다만 뒤의 것은 "실패에서 배워 가드를 만든다"는 접근이 실제로 시도되고 있다는 정도의 참고가 된다.

문제 사례로는 앞서 말한 Lovable 취약점 보고가 있다. 여기서 얻을 교훈은 비슷하다. 테스트 없이 AI 코드를 병합하지 말 것. 에이전트가 같은 실수를 반복하면 가드나 훅으로 막을 것. 외부 도구의 기능은 바뀔 수 있으니, 그 점을 전제로 워크플로를 설계할 것.

일반적인 작업 흐름도 소개해 둔다. 웹 앱이라면 요구사항을 PRD와 CLAUDE.md로 정리하고, 스캐폴드를 만든 뒤, 기능 단위로 구현한다. 테스트와 린트 결과를 보고 고치고, 커밋과 배포로 마무리한다. 서브에이전트로 일을 나눌 수도 있다. 메인 세션이 계획을 세우고, 조사 서브에이전트들이 병렬로 자료를 모으고, 작성 서브에이전트가 초안을 쓰고, 메인 세션이 검토한다.

이 글이 바로 그런 방식으로 만들어졌다. 트렌드, 장단점, 사례를 맡은 조사 에이전트 3개를 병렬로 돌렸고, 작성 에이전트가 그 결과로 초안을 썼다. 그래서 아래 "발행 전 확인 필요" 목록이 필요하다. 에이전트가 쓴 글도 사람이 검증해야 한다.

### 단점을 줄이는 실천 체크리스트

위험은 대부분 습관으로 줄일 수 있다. 조사에서 정리된 방법은 다음과 같다.

- CLAUDE.md에 스택, 명령어, 규칙, 금지 사항을 적는다.
- 큰 변경은 계획 모드로 먼저 계획을 승인한다.
- 테스트, 타입 체크, 린트, 빌드 통과를 완료 조건으로 둔다.
- 작은 단위로 맡기고 diff를 직접 리뷰한다.
- 권한은 기본적으로 확인을 받는다. 안전한 명령만 허용 목록에 넣고, 시크릿은 거부 목록에 넣는다. 가능하면 샌드박스를 쓴다.
- 작업이 바뀌면 새 세션을 열어 컨텍스트를 관리한다.
- "왜 이렇게 했는지 설명해줘"라고 물어 이해했는지 확인한다.
- 구현 세션과 리뷰 세션을 분리한다.

### 어울리는 경우와 그렇지 않은 경우

잘 맞는 경우는 이렇다. 프로토타입, MVP, 사이드 프로젝트. 테스트와 문서가 갖춰진 코드베이스. 범위가 분명한 리팩터링, 테스트 작성, 문서 작업. 설명을 함께 요청하면서 하는 학습.

맞지 않는 경우도 있다. 인증, 결제, 개인정보 관련 코드를 검토 없이 배포하는 일. 요구사항이 불명확한 복잡한 레거시. 벤치마크 없는 성능 민감 코드. 기초를 배우는 단계에서 이해 없이 결과만 가져다 쓰는 일. 팀 규약 없이 각자 제각각 쓰는 상황.

## 결론

바이브 코딩은 검증을 대신해 주지 않는다. 에이전트가 빠르게 쓰는 만큼 사람은 더 엄격하게 검증해야 한다.

Claude Code의 기능 흐름이 보여 주듯, 도구도 훅, 권한, 워크트리, 관리형 설정 같은 통제 장치 쪽으로 발전하고 있다. 기업 사례의 수치는 인상적이지만 회사 발표이고, 일부는 Claude Code만의 효과가 아닐 수 있다. METR의 실험은 체감과 실제가 다를 수 있다고 말한다. 그러니 도입한다면 작게 시작하고, 완료 조건을 테스트로 정하고, 모든 diff를 읽는 습관부터 들이는 편이 좋다.

앞으로도 이 분야는 빠르게 바뀔 것이다. 이 글의 기능과 요금 정보는 2026년 11월 19일 기준이니, 쓰기 전에 공식 문서를 다시 확인하길 권한다.

## 발행 전 확인 필요

- METR 실험: 평균 약 19% 느려짐, 체감 약 20% 빨라짐. 장단점 조사가 웹 검색 없이 작성돼 원문 확인이 필요하다.
- Veracode 2025 GenAI Code Security Report: AI 생성 코드 샘플 약 45% 보안 결함. 원문 확인이 필요하고, 시험 과제 한정이라는 조건도 함께 확인해야 한다.
- GitClear의 중복·churn 증가 분석, Perry 외(ACM CCS 2023)의 결과: 원문 확인이 필요하다.
